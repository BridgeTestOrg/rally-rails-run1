> Greenfield standard: chosen before implementation code existed; revisit once the repository has real code.

Keep documentation small and operational: the root README.md covers setup, running and testing, and any further documents live in docs/ as descriptive lower-kebab-case Markdown files (for example docs/backup-and-restore.md); after a meaningful feature, migration, auth or deployment change, update or add the relevant document describing what changed and why, the important files and decisions, new configuration or credential names (never their values), and any migration or data-safety notes, and always keep the Litestream backup and restore procedure, Kamal deployment and secret setup, and migration recovery steps current because they protect against data loss; skip documentation for self-explanatory CRUD, internal refactors, test-only or style-only changes, and never add per-class docblocks or copies of Rails guides.
